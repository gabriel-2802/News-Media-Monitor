# Databases

This system uses two databases with a strict separation of concerns: **Neo4j** is the
system of record for everything except vectors, and **Qdrant** stores nothing but
vectors. Nothing else is duplicated between them except a shared ID (a Story's `id` in
Neo4j is the same string as its point ID in Qdrant).

## Neo4j — source of truth

Graph database holding every entity and relationship in the system. If it isn't a
vector, it lives here, and only here. Accessed exclusively through the **Provider**
service's REST API (`provider/`) — no worker talks to Neo4j directly.

**Nodes:**

| Node | Holds | Written by |
|---|---|---|
| `NewsSource` | name, base URL, RSS URL, failure count, disabled flag | Provider (admin/setup) |
| `Article` | author, title, url, full body text, publishedAt | Scraper worker |
| `Topic` | name | Classifier worker (topic taxonomy) |
| `Story` | title, createdAt, lastUpdated, articleCount, sourceCount, trendingScore | Clusterer worker |

**Relationships:**

```
(:Article)-[:FROM_SOURCE / PUBLISHED]->(:NewsSource)
(:Article)-[:HAS_TOPIC]->(:Topic)
(:Article)-[:BELONGS_TO]->(:Story)
```

**IDs:** every node's `@Id` is a UUID string generated by `UuidStringIdGenerator`
(`provider/src/main/java/data/provider/util/UuidStringIdGenerator.java`) and persisted
as a real `id` property. This matters because Spring Data Neo4j's default generator
(`InternalIdGenerator`) does *not* persist an `id` property — it only tracks Neo4j's
internal element ID — which silently breaks any custom Cypher that matches on
`{id: $x}` (this is exactly what happened with `Story` before the fix: `attachArticle`
always failed with "story does not exist" because there was no `id` property to match).

**No embeddings are stored in Neo4j.** `Story.trendingScore`, `articleCount`, etc. are
plain aggregates recomputed on every attach — Neo4j never sees a vector.

## Qdrant — embeddings only

Vector database holding exactly one collection: `story_centroids`. Nothing else about
a Story lives here — no title, no article text, none of Neo4j's fields except the two
needed to make the nearest-neighbor search useful.

**Collection: `story_centroids`**

| Field | What |
|---|---|
| Point ID | Same UUID string as the Story's `id` in Neo4j |
| Vector | 384-dim, cosine distance — the Story's running centroid embedding |
| Payload: `storyId` | Redundant copy of the point ID, for convenience when reading hits back |
| Payload: `articleCount` | Used to weight the running-average update when a new article attaches |
| Payload: `lastUpdated` | Datetime (indexed) — powers the recency-window filter on candidate search |

**Model:** `sentence-transformers/all-MiniLM-L6-v2` (384-dim), loaded by the singleton
`ArticleEmbedder` in `workers/clusterer/embedder.py`. Chosen over the larger
`Qwen/Qwen3-Embedding-0.6B` after validation showed only a marginal accuracy drop
(90.8% → 88.0% balanced accuracy — see `workers/clusterer/data/output/validation_report.md`)
for ~27x fewer parameters.

**Who touches it:** only the clusterer worker (`workers/clusterer/clusterer_worker.py`).
Scraper and classifier workers never see Qdrant.

**What it's used for:** the clusterer worker's attach-vs-create decision. For each new
article:
1. Embed the article's title + body.
2. Query `story_centroids` for the nearest point with `lastUpdated` within the last
   `RECENCY_WINDOW_DAYS` (5 days).
3. If the best match's cosine similarity ≥ `SIMILARITY_THRESHOLD` (0.533), attach the
   article to that Story and update its centroid as a running average (renormalized
   back to unit length, since cosine-as-dot-product only holds for unit vectors).
4. Otherwise, create a new Story and seed a fresh centroid point under its ID.

## Why split this way

- **Independent scaling/tuning.** The embedding model, similarity threshold, and
  recency window can all change without touching Neo4j's schema, and vice versa
  (adding a new Article field never touches Qdrant).
- **Qdrant's ANN index is the only thing that makes "find the nearest of N stories"
  cheap.** Neo4j has no efficient way to do a cosine-similarity nearest-neighbor
  search across thousands of centroid vectors; that's what Qdrant is for.
- **Consistency ordering differs by operation, and that's intentional:**
  - *Attach to an existing Story*: Qdrant is written first (upsert-by-ID is cheap to
    retry, so a crash before the Neo4j write just means the next redelivery
    re-computes the same update), then Neo4j.
  - *Create a new Story*: Neo4j is written first, because Story IDs are
    server-generated — there's no ID to seed a Qdrant point under until Neo4j assigns
    one. This is the one place the ordering flips, and it's why the code comments
    call it out explicitly.
- **Blast radius.** If Qdrant is down, scraping and classification keep working —
  only clustering stalls (RabbitMQ nacks and retries). If Neo4j is down, nothing
  works, which is correct: it's the actual source of truth.
